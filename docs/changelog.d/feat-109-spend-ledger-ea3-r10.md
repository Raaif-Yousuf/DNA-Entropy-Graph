- feat(app): monthly spend ledger and spending cap (#109). When a run row ends (any writer: runner, reconciler, cleanup) a `vm_runtime` CostLedger row is written once per run (migration 0003 adds a unique index on (RunId, Kind), duplicates removed first; the repository inserts with INSERT OR IGNORE; the run row is stored before the ledger row; the registered repository keeps the #113 phase guard). The booked span is one rule in one helper used by every path (runner create, reuse, adoption and resume, cancel, reconciler): it starts at the VM's own platform start from any observation of the VM and never at the app's clock; it ends at the VM's stop time if it stopped, at the last time the app knew a self-deleted VM was alive, or when the run ends if the VM is still running; a run that never observed a VM books nothing. A VM that stopped itself and is resumed hours later books the time it ran, not the time the app was closed; a cancel in a fresh process books the VM it finds. The rate is the machine's hourly rate (Spot rate for Spot) plus its boot disk; month-to-date is summed over the local calendar month and adds VM time accrued by runs still going ("includes runs in progress", capped at the run limit plus grace; a granted flex VM that is booting counts, a queued request does not). Settings > Spending adds a warning cap and a hard stop. The New run page shows a cap card (also with no file chosen; not for a This PC run), and with the hard stop on it turns red and disables Run; the engine asks the same shared path and refuses before anything is created with the new `spend_cap` error (action: Open Settings). Not counted: a VM kept alive or stopped after its run ended, time before the VM existed, bucket storage. All figures are estimates; #557 and #150 can read the same ledger. A gone VM with no sign of life books its start plus the run limit (the run's maximum plus the grace, one definition on the runner and reconciler paths) but never past now: a VM that died 5 minutes in and is found 10 minutes after it started books about 10 minutes, not the limit. The cloud runner records the worker's own heartbeat time on the run row (at most once a minute, from one row read, with the run's cancellation token, and only a heartbeat newer than the one already recorded, so a stale status.json found on a resume cannot move it; the time recorded is the earlier of the worker's own time and the app's now, so a VM clock ahead of the app's cannot store a future time, and a heartbeat that advanced with no readable time records the app's now). A booked span is never negative and a gone VM never ends after now. An adopted already-existing VM books from its own start, and a cancel that finds several VMs books the earliest start to the latest end.

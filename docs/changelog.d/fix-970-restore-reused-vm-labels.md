- A reuse that fails or is cancelled no longer leaves the borrowed VM under the dead job's labels (#970): once the VM is confirmed stopped (after a failed start, a run that failed after the relabel, a cancel, or a reuse that landed after the cancel gave up), `VmTerminator.RestoreDonorLabelsAsync` puts the donor's own labels back through the new `IComputeGateway.RestoreVmLabelsAsync`, so the run it came from finds it again by label and its keep-alive expiry applies. The write is read-then-write under the label fingerprint and leaves a VM a newer run has taken; it runs in the run's own project and account; the instance's labels are written first, then the boot disk's. A restore that fails changes nothing about the run's own failure and leaves the #938 by-name guards as the backstop. The run's row says what happened (restored, left to a newer run, not confirmed stopped, or failed with its error class and the Cloud page) and the diagnostics log gets a `donor-restore` line (job id, state, class). The #938 round 7 tests that needed the donor to stay relabelled now script the restore to fail.
- A reuse that fails without proof its start was never sent (a lost answer, a timeout) no longer hands the borrowed VM's labels back while that start may still land (#970, cold review round 2): the failed run starts the same late watch a cancel does, which stops the VM if the start lands and restores the donor's labels only afterwards (or after the grace when it never does). A boot disk write refused with 412 is re-read before the restore is reported (another owner leaves the VM alone, the failed job's labels still there is an error), a replay after a lost answer is reported restored, a restore is no longer promised a retry nothing makes, stale donors are dropped, and a Cancelled result keeps the restore outcome the cancel still has to write on the row.
- A reused VM's labels are restored more reliably (#970, cold review round 3): a watch that ends forgets only the donor of its own VM, never another VM's donor of the same job; the donor's instance labels are written before its boot disk (the labels every lookup reads come back first, a failed disk write no longer fails the restore), and a boot disk that a newer run already relabelled stops the restore before anything is written; a reuse watch that outlasts its window with the VM stopped now restores the donor and logs it; restore outcomes nobody took are dropped with the expired donors. A failed reuse of any kind that may have sent its start (including a poll timeout that falls back to a new VM) leaves the donor under the failed job's labels until the watch's grace has run.

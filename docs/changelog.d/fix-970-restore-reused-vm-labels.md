- A reuse that fails or is cancelled no longer leaves the borrowed VM under the dead job's labels (#970): once the VM is confirmed stopped (after a failed start, a run that failed after the relabel, a cancel, or a reuse that landed after the cancel gave up), `VmTerminator.RestoreDonorLabelsAsync` puts the donor's own labels back through the new `IComputeGateway.RestoreVmLabelsAsync`, so the run it came from finds it again by label and its keep-alive expiry applies. The write is read-then-write under the label fingerprint and leaves a VM a newer run has taken; it runs in the run's own project and account; the instance's labels are written first, then the boot disk's. A restore that fails changes nothing about the run's own failure and leaves the #938 by-name guards as the backstop. The run's row says what happened (restored, left to a newer run, not confirmed stopped, or failed with its error class and the Cloud page) and the diagnostics log gets a `donor-restore` line (job id, state, class). The #938 round 7 tests that needed the donor to stay relabelled now script the restore to fail.
- A reuse that fails without proof its start was never sent (a lost answer, a timeout) no longer hands the borrowed VM's labels back while that start may still land (#970, cold review round 2): the failed run starts the same late watch a cancel does, which stops the VM if the start lands and restores the donor's labels only afterwards (or after the grace when it never does). A boot disk write refused with 412 is re-read before the restore is reported (another owner leaves the VM alone, the failed job's labels still there is an error), a replay after a lost answer is reported restored, a restore is no longer promised a retry nothing makes, stale donors are dropped, and a Cancelled result keeps the restore outcome the cancel still has to write on the row.
- A reused VM's labels are restored more reliably (#970, cold review round 3): a watch that ends forgets only the donor of its own VM, never another VM's donor of the same job; the donor's instance labels are written before its boot disk (the labels every lookup reads come back first, a failed disk write no longer fails the restore), and a boot disk that a newer run already relabelled stops the restore before anything is written; a reuse watch that outlasts its window with the VM stopped now restores the donor and logs it; restore outcomes nobody took are dropped with the expired donors. A failed reuse of any kind that may have sent its start (including a poll timeout that falls back to a new VM) leaves the donor under the failed job's labels until the watch's grace has run.
- A reused VM's labels are restored more safely (#970, cold review round 4): the VM's own labels decide who owns it, so a boot disk still carrying a dead job's id no longer keeps the VM under the borrowing job's labels (the disk is written afterwards, best effort, only while it still carries that job's id, and any failure there leaves the restore `Restored`); no label is written while a reuse start that never answered may still land (the watch gives up with `NotRestored:StartUnanswered` in the `donor-restore` log line and the VM stays stopped, guarded by the by-name rules, #1052); a watch that ends drops only its own send, never a later attempt's donor of the same VM; and leftover donors are pruned when a watch or a run ends and when a released reuse will never be restored.
- The borrowed-VM label restore now follows one stated rule (#970, cold review round 5): labels are never written while the app's own start call is still pending; once that call has finished (answered, refused, cancelled or lost) and the VM has read stopped through the grace, they are restored. A watch that defers to a newer attempt only reports "start never answered" for a start still in flight; a reuse seen landed but never answered is restored by the watch instead of being forgotten; a donor is matched and forgotten by its own send only; a refused label write whose re-read finds the VM deleted is "gone", not an error; and the row sentence for "not restored" is in plain words and names the Cloud page.
- The borrowed-VM label restore rule is now exact and fully enforced (#970, cold review round 6): labels are never written while the app's own start call may still land, that is until it has answered, been refused, finished on the app's side, or been seen to land. A watch that kept deferring to a newer attempt restores the VM when the VM still carries the job's labels and reads stopped, stands down when the newer attempt recorded its own start for the same VM, and otherwise logs `NotRestored:DeferredNewerAttempt`; a stale watch can no longer consume or write for a later attempt's donor; and a reuse refused before anything was sent forgets its donor and send record.
- Restoring a borrowed VM's labels (#970, cold review round 7): a watch that kept deferring to a newer attempt no longer restores the labels when our own start call completed without an answer (Canceled or a lost answer): it logs `NotRestored:StartUnanswered`, because that path never waits out the grace. It restores only when the start answered, was refused, or was seen to land. If at give-up the VM reads RUNNING under this job's labels (the start landed during the deferral), the watch stops it (never deletes it), writes no label, and logs `NotRestored:DeferredStartLandedStopped` (or `DeferredStartLandedStopFailed`). The provisioner now forgets the donor in a `finally`, so a throwing failure funnel cannot leak it.

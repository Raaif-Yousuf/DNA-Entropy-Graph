- A reuse that fails or is cancelled no longer leaves the borrowed VM under the dead job's labels (#970): once the VM is confirmed stopped (after a failed start, a run that failed after the relabel, a cancel, or a reuse that landed after the cancel gave up), `VmTerminator.RestoreDonorLabelsAsync` puts the donor's own labels back through the new `IComputeGateway.RestoreVmLabelsAsync`, so the run it came from finds it again by label and its keep-alive expiry applies. The write is read-then-write under the label fingerprint and leaves a VM a newer run has taken; it runs in the run's own project and account; the boot disk goes first. A restore that fails changes nothing about the run's own failure and leaves the #938 by-name guards as the backstop. The run's row says what happened (restored, left to a newer run, not confirmed stopped, or failed with its error class and the Cloud page) and the diagnostics log gets a `donor-restore` line (job id, state, class). The #938 round 7 tests that needed the donor to stay relabelled now script the restore to fail.

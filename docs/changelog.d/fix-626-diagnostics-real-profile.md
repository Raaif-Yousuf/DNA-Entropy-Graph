MEASURED 2026-10-03: a run whose name was its own job id (and, by the same shape, a run's `jobs/<id>/` bucket prefix) put the job id on the scrub list while the run history copies it verbatim, so the final leak scan refused with rule `identifier` on `run-history.json` and no zip was written. A name or prefix that is exactly the run's own job id is now exempt from the scrub list; every other name, path and identifier (including a job id holding the Windows user name) is still scrubbed and checked. A refusal now carries the check that fired (`DiagnosticsLeakException.Rule`, `LeakRules`) and Settings traces that fixed word, never user text. `docs/threat_model.md` section 5b updated.

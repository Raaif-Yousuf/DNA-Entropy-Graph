- App: Fetch from NCBI on the New run page. An accession (and an optional range) is checked on this PC with the worker's own pattern (a test reads `entrez.py` and fails on drift), then one NCBI `esummary` request from this PC (the worker's pace of 3 a second, 30 second timeout, one retry on 429 and 5xx) confirms the record exists and is under the worker's 64 MiB read limit, before any cloud resource exists (Hard Rule 2). A missing record, a too-large record or an unreachable NCBI fails the run with its own code (`input_accession_invalid`, `_not_found`, `_too_large`, `_unreachable`), each naming one action, and the same checks run on the page when **Fetch record** is pressed, which also gives the pill its length and the cost estimate a size. The accession is shown as an NCBI record in the list and sent as `inputs[].accession` / `accessionRange` with no `path`; nothing is copied or uploaded for it, the worker fetches the record on the VM. The run folder and the manifest name keep the version and range (`NC_045512_2_100-500`). A killed accession run resumes with no upload, re-checking its recorded accession first. The Runs search matches the accession. Run again starts from the same accession. No API key is sent (v1 is keyless, job_contract.md section 3). DECISION (agent-made, reversible): the NCBI check is made by the app, not left to the worker, because only the app can refuse before a VM is billed. (#684)

- The worker identity is real in the code (issue #54): `GoogleIamGateway` creates (or adopts) the service account `dna-entropy-worker`, creates (or undeletes, or repairs) the custom role `dnaEntropyWorker` with exactly the four Compute permissions the VM needs, binds it at the project with a version-3 IAM condition that only matches VMs named `deg-*`, and binds `roles/storage.objectAdmin` on the results bucket only, never touching a binding it did not add and writing nothing on a second run. When an organization policy forbids service accounts it falls back to the default Compute Engine account with the same bindings and a yellow note (`WORKER_DEFAULT_ACCOUNT`). A refusal to act as the account is `PERMISSION_ACTAS` with the action Copy request for the project owner. Production still uses `FakeGcp` until #56.
  The write's answer is read: a setIamPolicy that comes back without the worker binding (or, on the project, without the deg- condition) fails with `WORKER_IDENTITY_NOT_APPLIED` instead of reporting success. A bucket etag conflict worded as a 412 re-reads and retries (three writes at most). A 412 is a precondition conflict only when it positively looks like one (reason `conditionNotMet` or precondition wording, no `constraints/`); every other 412 stays an organization-policy refusal. One shared rule serves the classifier, `GoogleApiErrors`, the Cloud Storage gateway (so an organization-policy 412 on the app-config write surfaces instead of reading as "another PC wrote it first") and the worker-identity gateway; reasons are read from Storage and Compute's `errors[].reason` as well as `details[]` (THEORY, unverified: Cloud Storage uses 412 for a failed precondition). The `CONDITION_NOT_MET` code counts as org policy only where there is no 412 to decide by. The default-account fallback is recognised by `iam.disableServiceAccountCreation` too, its yellow note now has one action (Continue), says the account may hold a broad role (in older projects often Editor) and that the results bucket is open to every workload running as it, and a missing default account is `WORKER_DEFAULT_ACCOUNT_MISSING` (one action: Open service accounts, a link to the project's Service Accounts page, since Turn it on cannot help once preflight enabled Compute) while a missing adopted account fails at once, with no pointless 30-second wait. There is no production caller of the worker identity yet (issue #606). A 409 on create followed by a 404 on read creates once more. The honest limit that any `deg-` VM's token can stop any other `deg-` VM is in the threat model. `Google.Apis.Storage.v1` is bumped to 1.76.0.4271.

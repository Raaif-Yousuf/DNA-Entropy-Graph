- The job reconciler now also enforces what a finished run's VM should look like (#530, part b of #59): at launch, a VM labelled `delete` that was only stopped is deleted, a running VM labelled `stop` is stopped, and a keep-alive VM past its expiry ends per its after-keep-alive choice (the window is held only for a run the worker finished with exit 0, Completed or PartiallyCompleted, exactly as `worker/vm/startup.sh` does; a Failed or Cancelled run ends at once), each found by job-id label and only for this installation. This installation's stopped VMs idle longer than the `idle_stopped_vm_hours` setting (default 72, range 1 to 720, no off switch: `0`, a negative or an unreadable value means 72 and any number above 720, however large, is clamped to 720; no Settings control yet: #556) are deleted. Deleting and stopping get their own, longer deadline than a lookup, and one run, VM or error never ends the pass early: the rest are still handled. The pass runs again when the connection comes back (`ReconcileOnReconnect`, single-flight: reconnects during a pass become at most one follow-up pass, and a pass ends once the lifecycle and idle sweep have run and reattached runs are handed to their own drivers, never when those runs end), and never drives a run something else already owns. `IComputeGateway` gains `ListByInstallationAsync`; `VmDescriptor` carries `Labels` and `StoppedAt`. An error nobody foresaw in one row, and a reconcile pass that throws, are written to `logs/app.log` under the app data folder as a job id and an error class only (new `IDiagnosticsLog`, a stand-in until Serilog lands). The `scripts/check_app_wiring.py` DI check no longer treats the constructor of a factory-registered type (`AddSingleton<T>(sp => ...)`) as container-injected, which had flagged `ReconcileOnReconnect(Func<JobReconciler>)` as an unregistered dependency.

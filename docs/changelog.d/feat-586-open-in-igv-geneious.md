- app: the Results page has Open in IGV and Open in Geneious (#586, stacked on #102). Open in IGV connects to IGV's batch port (default 60151, key `Viewer.IgvPort`) on loopback and sends `new`, `genome` (the run's .fasta), `load` for each .bedgraph, then `load` for each gene .gff3 (the Geneious-only `.geneious.gff3` is left out), one command at a time, reading IGV's one-line `OK` before the next; paths are double-quoted and a path with a line break is refused. If nothing listens, IGV is started with `-g <fasta>` and the tracks (no shell, one argument each). A running IGV that rejects a command or does not answer is reported, never answered with a second IGV. Open in Geneious starts Geneious with the run's .gb then .gff3 files. The program is the saved path (`Viewer.IgvPath`, `Viewer.GeneiousPath`), else autodetected under Program Files and the per-user Programs folder (`ViewerLocator`), else the user's Browse choice, which is saved; a program that will not start is forgotten so the next press asks again. Files are chosen from the run's output listing by the worker's writer names (`Core/Viewers/ExternalViewerFiles.cs`); an absent file is skipped, and a run with no track or no GenBank/GFF3 says so. Every failure is one message naming one action (`Results_Igv*` and `Results_Geneious*` in `Resources.resw`). Sockets and process launch sit behind `IIgvBatchClient` and `IViewerProcessLauncher`. No paths are logged. Unproven on a real IGV or Geneious: see `docs/ToTest.md`.
